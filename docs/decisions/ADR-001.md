# ADR-001: Definición de Topic, Key y Particiones en Kafka

>  **Estado:** Aceptado

**Contexto / problema**
RapidGo necesita una plataforma de datos capaz de capturar y procesar eventos operacionales en tiempo real. Específicamente para la variante de "Demanda por zonas", el problema a resolver es el manejo de picos de solicitudes que afectan la disponibilidad y el servicio. Para esto, es necesario diseñar una configuración de ingesta en Kafka que permita a Spark calcular con exactitud indicadores temporales (como pedidos/minuto por área geográfica), manteniendo el rendimiento del procesamiento distribuido.

**Opciones consideradas**

* Opción A: Crear el topic rapidgo_demanda_zonas con 3 particiones y usar zona como llave (key).

Ventaja: Distribuye la carga de trabajo para aprovechar el paralelismo de los 2 Workers de Spark disponibles en el clúster local de Docker. Al definir la zona como llave, los mensajes de la misma área van a la misma partición, garantizando el orden cronológico estricto obligatorio para no hacer fallar el cálculo temporal de pedidos/minuto en Spark.

* Opción B:Crear el topic rapidgo_demanda_zonas con 3 particiones y usar pedido_id como llave (key).
  Ventaja: Asegura una distribución perfectamente equitativa de los datos entre las particiones.
  Contra: Los eventos de una misma zona se dispersarían aleatoriamente entre los Workers, rompiendo el orden temporal necesario para que las ventanas de tiempo de Spark funcionen correctamente por área.
* Opción C: Crear el topic rapidgo_demanda_zonas con 1 partición y sin llave.

Ventaja: Configuración simple.
Contra: Todo el procesamiento recaería en un único Worker de Spark, dejando el resto de la infraestructura inactiva y creando un cuello de botella innecesario.

**Decisión tomada**

Se decide usar la opcion A, con base en los siguientes argumentos:

- Configurando 3 particiones es posible procesar el flujo de datos de manera concurrente entre los **2 Workers de Spark** que se crean en la infraestructura local de Docker. La Opción C (1 sola partición) generaría un cuello de botella al forzar a un solo Worker a procesar la totalidad de la carga mientras el otro permanece ocioso.
- En comparación con la Opción B (clave `pedido_id`), si se agrupa por `zona` desde Kafka se segmenta en base aun criterio que permite agrupar y separar la logica en grandes grupos, a diferencia del pedido, que normalmente no se repite. Ademas, al llegar los eventos agrupados por partición según su zona, la carga computacional en las agregaciones por ventana se reduce drásticamente.
