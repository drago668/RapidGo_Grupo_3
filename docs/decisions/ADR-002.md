# ADR-002 — Validar las reglas de negocio sin levantar el clúster

> **Estado:** Aceptado
> **Fecha:** 29 de octubre de 2026
> **Contexto del release:** v0.1.0-foundation → v0.2.0-streaming

# Contexto / problema

Entre el release v0.1.0 (22 de octubre) y el 29 de octubre construimos el núcleo delpipeline: el generador de eventos, el job de Spark Structured Streaming con sus
ventanas y salidas a Parquet, y el tablero de trabajo en ramas con PR. Con tres personas tocando el mismo repositorio, cualquier cambio podía romper dos cosas sin
que nadie lo notara: el **contrato del evento** (los campos que Kafka transporta y Spark interpreta) y los **umbrales de las alertas** (35/50 pedidos por minuto y 80
pedidos sin asignar).

El problema era cómo revisar eso en cada Pull Request. Levantar Kafka, Spark y el Data Lake completo toma varios minutos, depende de Docker y de la memoria del equipo,
y no es razonable repetirlo en cada push. Pero validar solo la sintaxis tampoco protege las decisiones de negocio.

## Opciones consideradas

**Opción A — Levantar el clúster completo en cada Pull Request.**
Ventaja: se prueba el pipeline real de punta a punta.
Contra: lento (varios minutos), frágil (Kafka o Spark pueden no arrancar por recursos del runner) y difícil de interpretar cuando falla: el error suele estar en la infraestructura y no en el código del compañero.

**Opción B — Validar únicamente la sintaxis de Python.**
**Ventaja:** rápido y simple.
**Contra:** un archivo con errores de negocio pasa en verde. No habría detectado, por ejemplo, que el evento de ejemplo no cumplía el contrato.

**Opción C — Separar reglas y contrato en módulos de Python puro y probarlos con pytest en cada Pull Request; el pipeline completo se demuestra localmente.**
**Ventaja:** segundos de ejecución, sin Kafka ni Spark, y las pruebas revisan decisiones reales del equipo (umbrales y contrato), no una copia.
**Contra:** no prueba el comportamiento del streaming real (ventanas, watermark,escritura de Parquet).

## Decisión tomada

Se adopta la **Opción C**. Las reglas de alerta viven en `spark/reglas.py` y el
contrato del evento en `producer/contrato.py`, ambos sin dependencias de Kafka ni
PySpark. GitHub Actions ejecuta en cada Pull Request hacia `Develop`:

1. validación de sintaxis (`compileall`),
2. pruebas de contrato, reglas y generador (`pytest`),
3. validación de `docker-compose.yml` (`docker compose config --quiet`).

El job se llama `validar` y se exige como condición para hacer merge a `Develop`.
El pipeline completo se sigue demostrando localmente con Docker.

## Evidencia

- **33 pruebas en 0,2 s** (contrato, reglas y producer con Kafka simulado), ejecutadas en cada PR y en cada push a `Develop`.
- **Run 40809506012 (fallido):** el PR de CI falló con `ImportError: cannot import name 'producer' from 'producer'`. La causa no era el workflow: `producer/producer.py` no existía en `Develop` porque el PR #17 aún no se había integrado. El CI detectó un problema real de integración **antes** del merge.
- **Run 40810469525 (exitoso):** PR #19 con el pipeline ya integrado; check `validar` en verde.
- **Run 40810707856 (exitoso):** push a `Develop` tras el merge del PR #19.
- **Hallazgo del contrato:** el evento de ejemplo de la Semana 1 traía `"zona": "Norte"` y `"estado": "creado"`, mientras Spark filtra `estado == "CREADO"`. Con esos
  valores, la alerta de capacidad nunca se habría disparado. Se corrigió `samples/example_event.json` en el mismo PR del CI.
